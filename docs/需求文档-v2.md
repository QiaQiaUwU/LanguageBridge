## 二、规划中 / 讨论过但还没做

### AI 真正的工具调用（Function Calling）能力
完整读了 MyLibrary 的 `mylib_agent.py`/`quill_agent.py`/`settings.py` 之后确认：Quill 的"每日一签""塔罗抽牌"这类快捷操作，底层不是简单的预填提示词，而是**真正注册给 AI 的工具函数**（`draw_tarot`、`fetch_rss`、`paipan_today` 等），请求里带 `tools`/`tool_choice` 参数，AI 自己判断要不要调用、调用哪个，调用结果再拼回对话里。这是标准的 function calling agent 模式。

目前 LanguageBridge 的 AI 助手（无论是悬浮面板还是完整页面）只是普通的单轮/多轮对话 + 几个预填提示词的快捷按钮，**没有真正的工具调用能力**。语言学习场景下，这类工具可以是：
- "把这个词标记为认识/加入词库"——AI 判断对话里提到某个词该收进词库，直接调用写库
- "开始一次针对性听写"——AI 建议复习哪些词后，直接触发听写会话而不是让你自己去点
- "查词典"——回答问题时如果提到某个不确定的词，AI 自己先查一遍本地释义库/词典API再回答
- "加一条学习待办/习惯打卡"——对应 `quill_agent.py` 里的 `_tool_todo_add`/`_tool_habit_add`/`_tool_habit_checkin`，这轮已经把待办/习惯的数据模型（`studyTodos.ts`）建好了，工具调用只是在这套已有能力上加一层"AI 可以直接调用"，不用再重新设计数据结构
- "记住一些我的情况"——对应 `_tool_remember`，比如"我这周要考六级"这种上下文记忆，让后续对话/建议更贴合

完整翻了一遍 `quill_agent.py` 里全部 `_tool_*` 方法（`fetch_rss`/`todo_add`/`todo_list`/`todo_done`/`habit_add`/`habit_checkin`/`habit_list`/`remember`/`remember_birth`/`remember_concern`/`paipan_*`/`draw_tarot`/`get_weather`/`count_books`/`find_books`/`set_timer` 等），大部分是塔罗/八字/天气这类跟读书场景强绑定的玩法，跟语言学习无关，可以跳过；上面列的几个是真正值得搬的。

实现方式：`shared/core/aiClient.ts` 的请求体加 `tools` 参数（Anthropic 和 OpenAI 兼容接口都支持标准的 tool_use/function_call 格式），返回里如果是 `tool_use` 类型就在前端执行对应函数（调 wordStore/studyTodos 的方法），把结果重新发回去继续对话，一个来回可能要 2-3 次请求。这是一次不小的改动，值得做但这轮没动，先记下来。

### 真正的发音评测
当前跟读模式的打分是"识别出的文字 vs 原文"的文本相似度，不评价语调、重音、口音地道程度。真正的发音评测（音素级别打分、语调曲线对比）需要接入专门的语音评测服务（通常付费，比如科大讯飞、Azure Speech 的发音评估 API）。如果愿意为此付费，可以后续接入，做法是在 `shared/core/` 下新增一个语音评测客户端，跟读模式录制的音频直接发给该服务而不是走浏览器免费的 Web Speech API。

### 按考试类型/分类的独立筛选维度
现在从释义库整库导入时，高中/CET6/考研/托福/雅思等分类是当"词书"处理的（一个词可能同时属于多个分类词书）。更彻底的做法是把"分类标签"做成一个和"词书"正交的独立筛选维度——比如同一个自建词书里的词，也能按"这个词同时是不是雅思核心词"来筛选。这个需要词汇中心筛选栏增加"标签"筛选行，数据结构上给 WordItem 加一个 `tags: string[]` 字段（区别于 `groupId` 词书归属）。工作量中等，值得做但这轮先没动，等你觉得需要了随时可以继续推进。

### 表格型 DOCX / 分栏 PDF 的精确解析
目前 DOCX/PDF 都是"提取整页纯文本再按行解析"，遇到严格的表格（单词|音标|释义三栏）或分栏排版（听力同义替换册子）容易错位。如果这类文件是你高频要导入的格式，值得专门针对表格结构写解析（docx 表格可以用 mammoth 的样式映射拿到表格结构而不是纯文本，pdf 分栏可以按坐标聚类而不是简单按 y 坐标顺序拼接）。

### 更完整的语音输入体验
现在跟读/复述录音用的是浏览器免费的 Web Speech API（Chrome/Edge only，底层调 Google 服务，国内网络可能不稳）。如果对准确率/稳定性有更高要求，可以接入付费的语音转文字服务（如 Whisper API）替换掉免费方案。

### GitHub 上找到的相关参考项目
搜了一圈跟 LanguageBridge 各个板块类似的开源项目，这些不是要照搬，是给你看看别人怎么处理同样的问题，有需要的话可以借鉴思路：
- **[Breedoon/BookSync](https://github.com/Breedoon/BookSync)** —— 有声书跟文字同步阅读，用 DeepSpeech 做强制对齐（音频转文字+对齐出每个词的时间戳）。这是"影子跟读自动裁剪音频"这个问题的真实技术参考——印证了自动对齐得跑语音识别模型，不是纯前端能做的
- **[vito-go/mywords](https://github.com/vito-go/mywords)** —— 输入网址自动提取生词+按认知等级（不认识/认识/熟悉/精通）过滤，思路很接近词汇中心那套认识/模糊/不认识的分级
- **[hikariming/openkoto](https://github.com/hikariming/openkoto)**（TextLingo）—— 导入任意文本/URL/PDF 用 AI 辅助学外语，一键翻译+生词提取，整体产品思路上最接近 LanguageBridge 的阅读助手部分
- **WhisperX**（工具本身，不是某个学习平台）—— 词级时间戳强制对齐的标准开源方案，如果以后真想做"自动裁剪音频对应句子"，这个是绕不开的技术选型，但需要一台能跑模型的服务器（GPU 更好），跟现在纯前端+轻量 Node 静态服务器的架构是两回事
- **LWT (Learning With Texts) / Lute** —— `awesome-language-learning` 这个列表里收录的经典自托管"通过阅读学外语"工具，选中生词标记状态、追踪进度这套东西是这类工具的标配，做法上跟词汇中心+阅读助手的整体思路一致，算是印证了现在这条路子是对的
